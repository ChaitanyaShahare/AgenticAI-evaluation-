# Architecture

The harness is **trace-first**: every run of the system under test, whatever framework built it, becomes one canonical
`Trajectory`. Evaluators, scoring, gates and reports read only that trajectory plus project configuration. Moving to a
new project means new configuration and, at most, one adapter — never a change to `evalkit/`.

## Design principles

1. **Grade every agent, not just the answer.** Each trajectory is sliced per agent; every run yields a scorecard for
   each of the five agents as well as the end-to-end verdict.
2. **Deterministic checks are the only gates.** LLM judges are advisory (S3, report-only) until calibrated against the
   testers (κ ≥ 0.6, ≥ 85% agreement).
3. **Oracles are human-owned data.** Policy rules, masking rules, gate thresholds, S1 expectations and the lab answer
   key are YAML written by the QE Lead, never generated by the assistant that builds the system.
4. **Never pass on missing evidence.** A check that cannot be computed is `skip` with a reason; an unmeasured threshold
   makes the gate `INCOMPLETE`, a blank gates file makes it `NO_GATES`.
5. **`evalkit/` never imports `projects/`.** Project code is loaded by the `module:attribute` references in
   `project.yaml`.
6. **Live calls are opt-in.** Every command that calls a model is a dry run with a cost estimate unless `--yes` is given.

## Components

```
configs/            eval.yaml (models, effort, run modes, trials, budget) · gates.yaml · judges.yaml · pii_recognizers.yaml
projects/<name>/    project.yaml · agents.yaml · tools/specs/*.json · policies/*.yaml · datasets/**/*.yaml
                    reference_trajectories/RT-*.json · sut/ (the system under test) · data/ (synthetic seed DB)
evalkit/
  config/           strict Pydantic loaders; registry (metric catalogue, evaluator lists, ProjectSuite)
  datasets/         case YAML loader, catalogue import, lint, coverage
  harness/          runner (plan k trials, parallel), per-trial DB sandbox, clock, fault hook, cost
  adapters/         AgentAdapter interface; LangGraphAdapter (run-event protocol → Trajectory)
  schema/           Trajectory, Step, ToolCall, RunMeta · TestCase · TrialRecord, CheckResult, CaseResult
  evaluators/       policy engine · trajectory/ · tooluse/ · bfsi/ · agent/ · judges/ · grader
  scoring/          composite (SOP §5.3), aggregate (per agent / pattern / suite), gates (verdict + exit code)
  reporting/        redaction, results.jsonl, junit.xml, report.html
```

## Data flow

```
case YAML ──► runner: plan case × trial (k per severity) ──► per-trial copy of the seed DB
                │                                               │
                ▼                                               ▼
           adapter.run(case, trial) ──► system under test (mocked tools, fault hook, clock, scripted customer,
                │                         mock approver) ──► run events + end state (SQL on the trial DB)
                ▼
           Trajectory (trajectories/<case>/t<k>.json)
                │
                ▼
           grader: trial evaluators · per-agent evaluators (on each agent's slice) · group evaluators
                   (pass^k, injection twins, fairness pairs) · optional judges
                │
                ▼
           CheckResults ──► composites + scorecards ──► gates.yaml ──► verdict + exit code
                │
                ▼
           results.jsonl · scorecard.json · gate.json · junit.xml · report.html · cost.json
```

`evalkit run / eval / gate / full` do the whole chain. `evalkit grade` and `evalkit report` start from stored
trajectories and make no model calls, so evaluator changes are re-checked for free.

## The canonical trajectory

`evalkit/schema/trajectory.py`:

| Model | Key fields |
|---|---|
| `RunMeta` | run_id, case_id, trial, project, adapter, models per role, effort, prompt hashes, package versions, seed, as_of, duration, token usage per model |
| `Step` | index, kind (`llm`, `tool`, `handoff`, `interrupt`, `message`, `user`, `guard`, `contract`, `decision`, `agent_result`, `note`), agent, tool_call, handoff_to, content, data |
| `ToolCall` | call_id, agent, tool, args, result, status (`ok` / `error` / `timeout`), attempt (per identical arguments), latency, `fault_injected` (set by the harness only) |
| `Trajectory` | meta, user_turns, steps, final_message, end_state (system of record after the run), agent_outputs, error |

Views used by evaluators: `tool_calls(agent)`, `tool_sequence(agent)`, `handoffs()`, `agent_slice(agent)`,
`messages()`. A run that crashed is still a Trajectory with `error` set, so it is graded rather than lost.

## Adapter and run-event protocol

`AgentAdapter.run(case, trial, run_id, db_path, client) -> Trajectory` is the only interface a project implements.
`LangGraphAdapter` calls the project's `runner` (named in `project.yaml`), which returns a run record whose
`state["events"]` is an ordered list of events — `run_start`, `llm`, `tool`, `handoff`, `interrupt`, `message`,
`user`, `decision`, `guard`, `contract`, `agent_result`, `canned_state` — documented in `evalkit/adapters/base.py`.
The end state comes from `project.yaml › end_state_query` run on the trial's database copy.

The OpenTelemetry adapter planned in SOP v0.3 was descoped in WP4: the KYC graph logs its own events, so a second
capture path added live-call cost without a second framework to justify it.

## Harness

| Part | What it guarantees |
|---|---|
| Runner (`harness/runner.py`) | k trials per severity (S1: 3), run sets smoke / gate / full, parallel trials (`execution.max_workers`, thread pool), run folder per run |
| Sandbox (`harness/sandbox.py`) | every trial starts from an identical copy of the seed database |
| Clock (`harness/clock.py`) | the fixed test date AS_OF = 2026-11-02 in every tool (document expiry, bill age) |
| Fault hook (`harness/fault_hook.py`) | per-tool, per-identical-arguments faults (timeout, 5xx, malformed, empty, slow) and overrides; stamps `fault_injected` on every outcome |
| Scripted customer and approver | served by the KYC mocks (`request_customer_info`) and the case's `approver` field |
| Cost (`harness/cost.py`) | tokens per model and agent; money only from configured prices; monthly ledger and alerts |

Determinism comes from the harness, not sampling settings (the API accepts no temperature): deterministic mocks, the
fixed clock, deterministic contract builders, effort pinned per role, k trials with pass^k, and a flaky-case report.

Run folder `<runs dir>/<run_id>/`: `manifest.json`, `trajectories/<case>/t<k>.json`, `trials.jsonl`,
`db/<case>/t<k>.sqlite`, and after grading `results.jsonl`, `scorecard.json`, `gate.json`, `junit.xml`,
`report.html`, `cost.json`. The judge cache and the monthly cost ledger live at the top of the runs folder.

## Evaluators

Each evaluator returns `CheckResult(metric, agent, rule, verdict, severity, score, detail, evidence_step)`; the
verdict is `pass`, `fail`, `skip` (with the reason) or `error` (an evaluator crash, which counts as a failure).

| Family | Metrics | Where |
|---|---|---|
| Policy engine | TR-3, TR-4, BF-2, TU-7, decision rules D1–D10, limits, TRANS-1, SLICE-1, VER-1, AG-5 guardrails | `evaluators/policy_engine.py` executing `policies/*.yaml` |
| Trajectory | TR-1 end state, TR-2 match, TR-5 hand-offs, TR-6 efficiency, TR-7 pass^k | `evaluators/trajectory/` |
| Tool use | TU-1 selection, TU-2 schema, TU-3 values, TU-4 grounding, TU-5 fault handling, TU-6 reconciliation | `evaluators/tooluse/` |
| BFSI | BF-1 PII / PCI, BF-3 injection twins, BF-4 prompt leak, BF-5 fairness pairs, BF-6 audit completeness | `evaluators/bfsi/` |
| Per agent | AG-1 … AG-6 on each agent's slice | `evaluators/agent/` |
| Judges (advisory) | TR-8.task, TR-8.plan, BF-4.explanation (0–3 rubric) | `evaluators/judges/` |

The registry (`config/registry.py`) lists the metric catalogue and the evaluator classes, and
`ProjectSuite.load(project)` builds everything an evaluator needs from configuration: tool specs (owner `x-agent`,
input schema), agents.yaml, policy and masking files, recognisers, limits and pinned versions from eval.yaml,
reference trajectories and cases.

The grader (`evaluators/grader.py`) runs trial evaluators per trajectory, per-agent evaluators per agent slice and
group evaluators per case or pair, records evaluator crashes as `error` checks, masks identifiers in every detail,
computes pass^k, and builds the scorecards.

## Scoring and gates

- **Composites** (`scoring/composite.py`, SOP §5.3): end-to-end `G × (0.40·TR-1 + 0.20·TR-2 + 0.20·TU-3 + 0.10·TU-5 +
  0.10·TR-6)`; per agent `G_X × (0.40·AG-1 + 0.25·AG-2 + 0.20·AG-3 + 0.10·AG-4 + 0.05·AG-6)`. G = 0 on any S1
  failure. Unmeasured components are left out, the weights rescaled and the components used are named. Trend only.
- **Aggregation** (`scoring/aggregate.py`): pass rate over checks run, mean score, S1 failures, per agent, pattern and
  suite.
- **Gates** (`scoring/gates.py`): applies `configs/gates.yaml`.

| Verdict | When | Exit |
|---|---|---|
| `NO_GATES` | gates.yaml blank | 2 |
| `SUSPENDED` | more than `flake_limit` of repeated cases are flaky (SOP §3.5) | 2 |
| `FAIL` | any S1 failure, or a measured threshold missed | 1 |
| `INCOMPLETE` | a threshold could not be measured | 2 |
| `PASS` | every S1 check passed and every threshold measured and met | 0 |

## Reporting

Everything rendered is redacted first (`reporting/redaction.py`: every recognised identifier masked to its last 4).
The finished `report.html` and `junit.xml` are scanned again; if an identifier survives, the report is not written and
the command fails (`ReportLeak`). JUnit test names carry the rule: `KYC-GLD-001 t1 · TR-3 (R1)`, so a CI annotation
names the failing rule. `results.jsonl` has one row per case × trial × check with its evidence step.

## CI

`.github/workflows/eval.yml`: smoke on every push (offline, plus 10 live golden cases when the `ANTHROPIC_API_KEY`
secret exists), the S1 gate on pull requests, the full run nightly at 02:00 IST. Each job uploads the reports and
publishes junit.xml as annotations. Not yet proven on GitHub: the repository has no remote yet.

## Extension points

| To add | Touch | Guide |
|---|---|---|
| A project | `projects/<name>/` only | `docs/extension_guide.md` |
| An agent framework | a new adapter in `evalkit/adapters/` | same |
| A metric or evaluator | `evalkit/evaluators/…` + registry + a good / bad test | same |
| A rule | the project's policy YAML (human-owned) | `docs/config_reference.md` |
| A judge rubric | `evaluators/judges/` + `configs/judges.yaml` | same |
| A fault type | the fault hook behaviours + the project's fault profiles | same |
| A PII recogniser | `configs/pii_recognizers.yaml` | same |
